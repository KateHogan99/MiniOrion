# Day 8 — Guidance, Control, and GNC Validation

## Overview

Day 8 extends the spacecraft simulation from a physics propagation model into a basic **Guidance, Navigation, and Control (GNC)** system.

The major goal of this iteration was to move beyond simply simulating a spacecraft's motion and begin answering a more important question:

> Can the system determine where the spacecraft should go, generate an appropriate control command, execute that command through the simulation, and validate that the resulting trajectory behaves as expected?

This iteration introduces three new modules:

* **Guidance** — determines a desired trajectory and acceleration required to move between two states.
* **Control** — converts the desired acceleration into a physically constrained thrust command.
* **GNCValidation** — evaluates whether the resulting maneuver satisfies its intended requirements and whether the simulated trajectory follows the planned trajectory.

The underlying simulation, numerical integration, orbital mechanics, and validation infrastructure from previous iterations remain in use.

---

## Day 8 Objectives

The primary objectives for this iteration were:

* Introduce a basic Guidance module.
* Introduce a basic Control module.
* Connect Guidance and Control to the existing simulation.
* Implement a cubic trajectory for point-to-point maneuvers.
* Constrain commanded acceleration to a maximum value.
* Validate the mathematical boundary conditions of the planned trajectory.
* Validate the simulated trajectory against the planned trajectory.
* Validate intermediate position and velocity tracking.
* Validate the maximum commanded thrust acceleration.
* Validate the final position and velocity.
* Validate that the maneuver runs for the intended duration.
* Preserve the validation-first mindset established in Day 7.

# 1. Guidance

The Guidance module defines a desired trajectory between an initial state and a desired final state.

A maneuver is represented by:

```cpp
struct ManeuverRequest
{
    State initial_state;
    State desired_state;
    double maneuver_duration;
};
```

The guidance system accepts:

* Initial position
* Initial velocity
* Desired final position
* Desired final velocity
* Maneuver duration
* Current elapsed time

It produces a `GuidanceCommand` containing:

* Position error
* Velocity error
* Desired position
* Desired velocity
* Desired acceleration
* Time remaining

## Cubic Trajectory

The current trajectory planner uses a cubic polynomial independently in the X and Y directions:

$$
r(t)=r_0+v_0t+c_2t^2+c_3t^3
$$

where:

* $r_0$ is the initial position
* $v_0$ is the initial velocity
* $c_2$ and $c_3$ are calculated trajectory coefficients
* $t$ is elapsed maneuver time

The coefficients are selected so that the trajectory satisfies both position and velocity boundary conditions:

$$
r(0)=r_0
$$

$$
v(0)=v_0
$$

$$
r(T)=r_f
$$

$$
v(T)=v_f
$$

The resulting velocity and acceleration profiles are:

$$
v(t)=v_0+2c_2t+3c_3t^2
$$

$$
a(t)=2c_2+6c_3t
$$

This provides a simple way to generate a smooth reference trajectory between two states.

### Why a Cubic Trajectory?

A cubic polynomial is the lowest-order polynomial capable of independently satisfying:

* Initial position
* Initial velocity
* Final position
* Final velocity

It therefore provides a useful first trajectory-planning method without introducing the complexity of a full orbital guidance algorithm.

It is important to note that this is **not yet an orbital guidance algorithm**. It is a simple point-to-point trajectory planner intended as a foundation for more sophisticated GNC work.

# 2. Control

The Control module receives the desired acceleration generated by Guidance and converts it into a thrust command.

The control configuration currently defines a maximum acceleration:

```cpp
struct ControlConfig
{
    double acceleration_constraint;
};
```

The resulting control command contains:

```cpp
struct ControlCommand
{
    Vector2D thrust_acceleration;
    double thrust_duration;
};
```

The Control module performs a simple saturation operation.

If the requested acceleration is within the available limit, it is passed through unchanged.

If it exceeds the limit, its magnitude is scaled down while preserving its direction.

Conceptually:

$$
a_{command} =
\begin{cases}
a_{desired}, & |a_{desired}|\leq a_{max}\
a_{desired}\frac{a_{max}}{|a_{desired}|}, & |a_{desired}|>a_{max}
\end{cases}
$$

This establishes the basic relationship:

```text
Guidance
   ↓
Desired acceleration
   ↓
Control
   ↓
Constrained thrust acceleration
   ↓
Simulation
```

The current Control implementation is intentionally simple. More sophisticated control laws can be introduced in later iterations.

---

# 3. Guided Maneuver Simulation

Guidance and Control are now connected to the existing simulation infrastructure.

The guided maneuver begins with an initial state and repeatedly:

1. Determines the current state.
2. Calculates the desired trajectory state.
3. Calculates the desired acceleration.
4. Passes that acceleration through the Control module.
5. Applies the constrained thrust command to the simulation.
6. Propagates the spacecraft state.
7. Records the resulting `SimulationStep`.

This creates a basic closed-loop guidance/control architecture rather than a manually specified thrust profile.

# 4. GNC Validation

Day 7 established validation as a central part of the project.

Day 8 extends that philosophy to the GNC system.

The `GNCValidation` module is responsible for determining whether the guided maneuver actually satisfies its requirements.

The current validation suite includes:

* Boundary-condition validation
* Intermediate trajectory validation
* Acceleration-constraint validation
* Command-duration validation
* Final-position validation
* Final-velocity validation
* Maneuver-duration validation
* Simulated-versus-planned trajectory validation

The intent is to distinguish between:

> "The simulation produced an answer."

and:

> "The simulation produced an answer that satisfies the requirements we gave it."

---

# 5. Boundary-Condition Validation

The cubic trajectory is mathematically constructed to satisfy four boundary conditions.

The validation module independently reconstructs the trajectory from the calculated coefficients and verifies:

### Initial position

$$
r(0)=r_0
$$

### Initial velocity

$$
v(0)=v_0
$$

### Final position

$$
r(T)=r_f
$$

### Final velocity

$$
v(T)=v_f
$$

This is an important distinction from validating the final simulation result.

The boundary-condition test asks:

> Did the trajectory generator itself produce the mathematical trajectory it was supposed to produce?

This isolates the Guidance calculation from the simulation and Control system.

---

# 6. Intermediate Trajectory Validation

Validating only the final state is insufficient.

A maneuver could theoretically arrive at the correct final position and velocity while following an incorrect trajectory in between.

Day 8 therefore compares every recorded simulation state against the analytically calculated cubic reference trajectory.

For each simulation timestep, the validation system calculates the expected position:

$$
r(t)=r_0+v_0t+c_2t^2+c_3t^3
$$

and expected velocity:

$$
v(t)=v_0+2c_2t+3c_3t^2
$$

The differences between the simulated and expected states are then calculated.

The validation records the maximum:

* Position trajectory error
* Velocity trajectory error
* Time at which each maximum error occurred

The maneuver passes only if both remain within their configured tolerances.

This provides substantially more information than simply checking the final state.

---

# 7. Acceleration Constraint Validation

The Control module imposes a maximum acceleration constraint.

The validation module examines the thrust acceleration recorded throughout the simulation and determines the maximum commanded acceleration magnitude.

The validation then checks:

$$
\left|a_{command}\right| \leq a_{max}+\epsilon
$$

where the configured tolerance accounts for numerical floating-point effects.

This verifies that the Control module is actually respecting its physical constraint.

---

# 8. Final State Validation

The final simulated state is compared against the requested maneuver endpoint.

### Position

$$
e_r=\left|r_{desired}-r_{final}\right|
$$

### Velocity

$$
e_v=\left|v_{desired}-v_{final}\right|
$$

The maneuver passes when both errors are within their configured tolerances.

This provides the final end-to-end test of the maneuver.

---

# 9. Maneuver Duration Validation

The simulation is also checked to ensure that its final recorded timestep corresponds to the requested maneuver duration within the configured tolerance.

This prevents a maneuver from being declared successful simply because its final state happens to be close to the target while the simulation itself ran for the wrong amount of time.

---

# 10. Validation Architecture

The GNC validation system is deliberately divided into separate tests rather than one large pass/fail calculation.

Conceptually:

```text
                 GNC Validation
                       |
        +--------------+--------------+
        |              |              |
   Mathematics     Simulation      Constraints
        |              |              |
 Boundary          Intermediate    Acceleration
 Conditions        Trajectory      Command Duration
        |              |              
        +--------------+--------------+
                       |
                Final State
                       |
              Maneuver Duration
```

This makes it possible to determine *why* a maneuver fails rather than simply reporting that it failed.

# 11. Example Maneuver

The current demonstration maneuver moves the spacecraft from:

```text
Initial position:  (0, 0) m
Initial velocity:  (0, 0) m/s
```

to:

```text
Desired position:  (100, 50) m
Desired velocity:  (0, 0) m/s
```

over:

```text
10 seconds
```

with an acceleration constraint of:

```text
100 m/s²
```

The simulation currently uses:

```text
Gravity:       Disabled
Integrator:    RK4
Time step:     0.05 s
```

This intentionally simple test case makes it easier to isolate the behavior of Guidance and Control from orbital mechanics.

# 13. Current Limitations

This iteration intentionally does not attempt to make the simulator a complete spacecraft GNC system.

Current limitations include:

* The trajectory planner is a simple cubic point-to-point planner.
* The model currently operates in two dimensions.
* Guidance does not account for orbital mechanics when generating its reference trajectory.
* Control currently uses simple acceleration saturation.
* The Control law has not yet been developed into a more sophisticated feedback controller.
* The maneuver does not yet model realistic spacecraft thruster behavior.
* The current interface is primarily intended for development and testing rather than general users.
* The validation framework is still specialized around the current maneuver architecture.
* The various capabilities of the growing simulation library are not yet exposed through a unified simulation interface.

These are intentional future development areas rather than unfinished requirements for Day 8.

# 15. Day 8 Result

Day 8 establishes the first complete GNC loop in the project:

```text
Maneuver Definition
        ↓
     Guidance
        ↓
Desired Trajectory
        ↓
      Control
        ↓
Constrained Thrust Command
        ↓
    Simulation
        ↓
   State History
        ↓
   GNC Validation
        ↓
 PASS / FAIL
```

The project has now progressed from a spacecraft physics simulator toward a basic spacecraft **Guidance, Navigation, and Control simulation framework**.

The most important architectural addition is not simply the ability to move the spacecraft from one point to another. It is the ability to define an intended maneuver, execute it through separate Guidance and Control components, and independently evaluate whether the resulting behavior satisfies the maneuver's requirements.

**Day 8 is considered complete.**
